# Respectful Meet — E2EE security model (v1)

## What is protected

New text messages are encrypted in the browser with Web Crypto before they are sent to the API. The server stores only the ciphertext envelope (`ciphertext`, `nonce`, sender public identity key) and never receives plaintext text for new E2EE messages.

- Identity: P-256 ECDH key pair generated by the browser.
- Private key: non-extractable `CryptoKey` stored in IndexedDB; it is never sent to the server.
- Key agreement: ECDH + HKDF-SHA-256.
- Message encryption: AES-256-GCM with a fresh 96-bit nonce per message.
- AAD binds the ciphertext to the conversation and protocol version.
- Server rejects plaintext message payloads.
- Browser uses a per-conversation TOFU fingerprint. If the peer identity fingerprint changes, sending/decryption is blocked and a security warning is shown.

## MITM limitation and user verification

TLS protects the transport. E2EE prevents a network observer, database reader, or ordinary server operator from reading ciphertext. However, a malicious server that can replace a peer's public key on the *first* contact can perform an active key-substitution attack unless users verify the peer fingerprint through an independent channel.

Therefore v1 implements TOFU and key-change detection, not an unconditional cryptographic claim of "zero MITM". Before production, the product should expose a safety-number/fingerprint verification UI and consider an audited Signal/MLS implementation for forward secrecy, multi-device sessions, and stronger identity authentication.

## Moderation trade-off

Because the server cannot read E2EE plaintext, server-side content inspection cannot inspect message text without breaking E2EE. The client performs the existing safety checks before encryption. Reports/moderation must be designed around user-submitted evidence and metadata rather than silently decrypting messages on the server.
