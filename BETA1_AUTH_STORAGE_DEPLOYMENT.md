# Respectful Meet Beta 1 — Free deployment (Vercel + Render + Neon)

This guide replaces the previous Cloudflare Pages / SnapDeploy / Aiven deployment notes for the new beta setup.

## Target architecture

- **Frontend:** Vercel static Vite deployment (`frontend/`)
- **Backend:** Render Docker web service (`backend/`, FastAPI)
- **Database:** Neon PostgreSQL (`DATABASE_URL`)
- **Authentication:** existing FastAPI username/password + Argon2id + server-side sessions; do not migrate to Neon Auth for this beta
- **API path in the browser:** same-origin `/api/v1` proxied by Vercel to Render
- **Media path for local beta storage:** same-origin `/media` proxied by Vercel to Render

No paid custom domain is required for the initial test. GitHub is the source repository.

## Important free-tier limits

Render's free web service sleeps after 15 minutes without inbound HTTP or WebSocket activity and takes about a minute to wake. Its filesystem is ephemeral: local uploaded photos/media can disappear after a restart, sleep, or redeploy. Use this deployment only for a beta/test. Configure S3-compatible object storage (for example, a free-tier storage account) before relying on persistent user media.

Neon is used for persistent relational data. Do not use Render's free PostgreSQL database for this setup.

## 1. Create Neon PostgreSQL

1. Create a Neon project and database.
2. Copy the PostgreSQL connection string.
3. Prefer the pooled hostname for runtime if Neon provides it; for this single small Render instance, a direct connection also works.
4. Ensure the connection string includes SSL (`sslmode=require`).
5. Never commit the connection string to GitHub.

Set this as Render's `DATABASE_URL`.

## 2. Create the Render backend

The repository includes `render.yaml` and `backend/Dockerfile`.

1. In Render, choose **New → Blueprint** and connect the GitHub repository.
2. Render reads `render.yaml` and creates the `respectful-meet-api` Docker web service on the Free plan.
3. In the service's Environment settings, set:
   - `DATABASE_URL`: Neon connection string
   - `CORS_ORIGINS`: exact production Vercel origin, e.g. `https://YOUR-PROJECT.vercel.app`
4. Keep `SECRET_KEY` generated by the Blueprint; do not replace it with a weak value.
5. Confirm `ALLOWED_HOSTS` includes the Render service hostname and `*.vercel.app`.
6. Confirm the health check `/api/v1/health/ready` returns ready after migrations finish.

The Dockerfile runs `alembic upgrade head` before starting Uvicorn and listens on Render's `PORT` (10000 fallback).

If Render assigns a different service hostname than `respectful-meet-api.onrender.com`, update the external rewrite destinations in `frontend/vercel.json` to the actual URL.

## 3. Deploy the frontend to Vercel

1. Import the same GitHub repository into Vercel.
2. Set **Root Directory** to `frontend`.
3. Framework: Vite.
4. Build command: `npm run build`.
5. Output directory: `dist`.
6. Add environment variable `VITE_API_BASE_URL=/api/v1` for Production (and Preview only if the preview backend/CORS is configured).
7. Deploy.

`frontend/vercel.json` contains:
- external rewrites for `/api/v1/*` and `/media/*` to Render
- no-store response headers for API responses
- SPA fallback to `/index.html` for React Router deep links

The same-origin API proxy is intentional: it lets the browser use the Vercel origin for API cookies instead of relying on cross-site third-party cookies.

## 4. Configure CORS and verify proxy

After Vercel gives the stable production URL:

1. Set Render `CORS_ORIGINS` to that exact HTTPS origin (no trailing slash).
2. Ensure `ALLOWED_HOSTS` includes the Render hostname and `*.vercel.app`.
3. Redeploy/restart Render.
4. In the browser, open `https://YOUR-PROJECT.vercel.app/api/v1/health` and confirm JSON status `ok`.
5. Open `/api/v1/health/ready` and confirm database status `ready`.

API and media rewrites must remain uncached. Do not add caching to authenticated API responses.

## 5. Beta feature configuration

Optional integrations may remain disabled during the zero-budget beta:

- Telegram payments: disabled until bot token and webhook secret are configured.
- Web Push: disabled until VAPID keys are configured.
- Admin OTP: requires SMTP only if `ADMIN_ALLOWED_EMAILS` is configured; otherwise do not enable admin OTP.
- Ads: keep `ADS_ENABLED=false` and mock mode enabled for testing only.
- S3-compatible media: recommended for persistent uploads; local Render storage is temporary.

Regular user signup/signin uses username + password and does not require SMTP.

## 6. Testing checklist

- [ ] Frontend loads on Vercel and deep links (e.g. `/signin`) do not 404.
- [ ] `/api/v1/health` returns `ok` through the Vercel proxy.
- [ ] `/api/v1/health/ready` confirms Neon connectivity.
- [ ] Signup, signin, `/auth/me`, and logout work with the HttpOnly session cookie.
- [ ] Two separate accounts can view profiles and start a conversation.
- [ ] E2EE messages remain ciphertext at the backend.
- [ ] Photos upload and load; remember local Render media is ephemeral until S3 storage is configured.
- [ ] Incoming-call WebSocket and call signalling WebSocket upgrade successfully through the Vercel rewrite.
- [ ] WebRTC audio/video tested on two different networks; STUN-only may fail behind restrictive NATs without TURN.
- [ ] Push, Telegram, and admin OTP are tested only after their optional credentials are configured.

Do not declare the app production-ready until the full checklist passes on the deployed URLs.
